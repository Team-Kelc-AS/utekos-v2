# Sporingsreparasjon og overtakelse

Status 10. oktober 2026: backendrettelsene er deployet, og søkesporing er fjernet fra publisert web-GTM. V2 er gjennomgått og testet for publisering til main via `pnpm run sync`; konkret commit/push-status kontrolleres i Git. Storefront-trafikken er ikke flyttet til v2. `utekos-headless` er pensjonert og skal aldri publiseres igjen.

Brukeren har godkjent deploy, GTM-endringer og overføring av eksisterende workers. En nyere instruks fra Utekos Brand Studio sier likevel «ingen bakgrunnsjobber». Derfor er backendinngang, køpublisering, workers og cron-aktivering fortsatt avslått. Dette er en instruksjonsbegrensning, ikke manglende brukerautorisasjon.

## Gjenstående steg

1. **Backenddrift og én eier.** Avstem eksisterende ni cron-planer, workflows, gammel kø/backlog og provider-outbox før overføring. Køer er prosjekt-/deploymentbundet; nytt backendprosjekt arver ikke automatisk gammel backlog. Privat konsumenttrigger mangler. Brukerens godkjenning er gitt; aktuell instruksjonsbegrensning hindrer aktivering. [Konkret overtakelsesplan](backend-worker-cutover.draft.md).
2. **Produksjonsbro og avhengigheter.** Verifiser positiv OIDC fra riktig prosjekt, avvisning av preview/manipulerte påstander, faktisk Redis-forbindelse, miljønavn/scope og providerkonfigurasjon. Inngangen må være tilgjengelig før dette kan bevise fungerende innsamling.
3. **Shopify checkout.** `read_pixels` ble avvist. Tom app-scope-webhookliste beviser ikke butikkglobal tilstand. Bekreft produksjonspixel, abonnenter, rå HMAC/checkout-OIDC, betalt ordre og refusjon med én autoritativ eier.
4. **Samordnet storefront/GTM-overtakelse.** Koble eksisterende Vercel-prosjekt til aktiv v2-kilde når backend kan betjene reisen. Verifiser produksjonsmiljøene, og bygg inn tracking-opt-in først da. PageLoad-utkastet er rebassert mot uendrede tagger i live 174, men fortsatt upublisert; browser-PageView skal ikke pauses før CAPI faktisk leverer.
5. **Korrelert produksjonsreise.** Følg Chrome/Safari, faktisk annonseklikk-ID, Cookie Keeper og checkout/Klarna med samme event-/journey-ID i browser → backend → ledger → outbox → provider. Naturlig eller særskilt godkjent kjøp/refusjon må dokumentere mottak, deduplisering og rapportert konvertering hver for seg. Ikke aktiver annonser før dette er avklart.

**Meta- og Microsoft-annonsering er ikke produksjonsklarert for v2 ennå.** Kode, deploy, lagring, provider-mottak, deduplisering og attribusjon er separate bevisgrenser.

## GTM og Stape

Web-GTM er nå live 174; server-GTM 44 ble lest i audit. Servercontaineren har GA4 og ingen Meta-/Microsoft-servertagger. Pausede Meta-tagger er fortsatt pausede. Data Tag-fordelingen videreføres.

Audit av Stape `gqnrnczg` viste ingen containeradvarsler og aktiv Custom Loader, AdBlocker, Cookie Keeper, AI Traffic Detection, Geo Headers, User Agent Info, User ID, Storage, Click ID Restorer, Product Feed og Enricher. Product Feed-synk var av, og Monitoring returnerte 409. Faktisk berikelses-/POAS-konsum og Safari-kontinuitet gjenstår. Ingen Power Up er endret.

`operator_policy` med granted beholdes som tidligere brukerbeslutning. Dette er ikke et registrert brukervalg eller bevis på juridisk samsvar.

## Git-publisering og lokal MCP-konfigurasjon

Første v2-push ble avvist av GitHub Push Protection fordi en eldre upublisert commit inneholdt en GCP-nøkkel i `.vscode/mcp.json`. De to upubliserte commitene ble ryddet etter [GitHubs fremgangsmåte](https://docs.github.com/en/code-security/how-tos/secure-your-secrets/work-with-leak-prevention/push-protection-on-the-command-line). Remote-historikken ble beholdt; ingen force-push eller omgåelse av skanningen ble brukt. Lokal Stitch-konfigurasjon er bevart uendret og ignorert av Git. Hemmeligheten ble ikke skrevet til verifikasjonsrapporten.

Sanitert sporingscommit før denne statusoppdateringen: `3cd518bb1e2507d881398e39b834ec4a0307e6f6`. Alle filer er identiske med det testede treet, bortsett fra `.gitignore` og at lokal MCP-konfigurasjon ikke lenger spores. Publisering følger fortsatt `pnpm run sync`; konkret remote-SHA bekreftes etter push. Gjenopprettingsreferanse er beholdt lokalt utenfor branch-navnerommet.
